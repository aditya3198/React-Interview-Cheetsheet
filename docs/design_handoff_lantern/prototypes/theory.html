Chapter 5 · JavaScript · Theory

The event loop, drawn out.

A single-threaded engine, two queues, one rule. Understand the rule and asynchronous JavaScript stops being surprising.

14 min read · updated may 2026 · covers ES2024 · ★ pin chapter

JavaScript runs on one thread. Every piece of code you write — a click handler, a network response, a setTimeout — eventually executes on the same line, taking turns. The event loop is the rule that decides whose turn is next, and it has been the source of "wait, why did it log that first?" since the language existed.

There are three pieces to keep in mind: the call stack, the macrotask queue, and the microtask queue. The stack is where synchronous code runs, one frame at a time. The queues are where callbacks wait until the stack is empty. The trick is that the two queues drain on different rules.

The rule, in one sentence

After every macrotask completes (including the first script load itself), the engine drains every microtask in the queue — including microtasks that other microtasks added — before pulling the next macrotask.

"Promises win ties." — the only mnemonic you need.

Worked example

The classic ordering question — what does this log?

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve()
  .then(() => console.log('3'))
  .then(() => console.log('4'));
console.log('5');

// ▸ "1"
// ▸ "5"   ← synchronous code finishes first
// ▸ "3"   ← microtask queue drains next
// ▸ "4"   ← chained .then is also a microtask
// ▸ "2"   ← macrotask runs only after microtasks empty

Both '3' and '4' land before '2' because the engine refuses to leave the microtask queue half-empty. Even if you added a thousand chained .then calls, they would all run before that 0 ms timeout.

!

The infinite-microtask footgun

Because microtasks drain completely before the next macrotask, a function that keeps re-queueing itself with queueMicrotask will starve every other task — including setTimeout, I/O callbacks, and browser rendering. The page freezes. Use setTimeout(fn, 0) when you want to yield back to the loop.

Why this matters for interviews

The event loop is the most-asked concept in JavaScript interviews because it sits at the intersection of everything else: promises, async/await, browser rendering, debouncing, and the difference between process.nextTick and setImmediate in Node. If you understand the rule above, every follow-up question reduces to "which queue?"

  • async/await is sugar over promises — every await point becomes a microtask.
  • Browser rendering happens between macrotasks (not microtasks), which is why a long microtask chain can block paint.
  • requestAnimationFrame is its own queue, drained before the next paint, after microtasks.

What to remember

Walking into the room with three sentences in your back pocket is enough:

  1. One thread, two queues. Microtasks (promises, queueMicrotask) and macrotasks (setTimeout, I/O, click).
  2. Microtasks drain completely between every macrotask.
  3. Rendering sits between macrotasks, so long microtask chains block the screen.
